1. Data Representation

1.1 Single trajectory

A single 3D spiral trajectory is a multivariate time series — a sequence of T observations, each recording three spatial coordinates at one instant in time:

$$\tau = \{(x_t, y_t, z_t) \in \mathbb{R}^3 : t = 0, 1, \ldots, T-1\} \iff \tau \in \mathbb{R}^{T \times 3}$$

Definition specific to this project's data generator (trajectory.py); not drawn from external literature.

Professor comment — §1.1 justified
"Are these all the same trajectories just with different noise? It might help to also vary other parameters to get richer training data."

The trajectories are not copies of one clean spiral with different noise draws. For every one of the N trajectories, the generator independently samples four physical parameters — starting radius $r_0$, radius growth rate $k$, vertical speed $v_z$, and total arc $t_{\max}$ — from fixed uniform ranges (see §2.1), then draws an independent Gaussian noise realization on top. Each trajectory in the dataset is therefore geometrically distinct, not a noisy repeat of a shared template.revised

The current parameterization varies 4 scalars per trajectory. Richer variation — initial phase offset, angular velocity, starting height, lateral centre offset, or 3D orientation — is a natural extension for future work, but is not implemented in the current codebase (trajectory.py); this reference describes the system as built, not a proposed extension.

1.2 Full dataset

The complete synthetic dataset consists of N independently generated trajectories, forming a rank-3 tensor X ∈ ℝ^(N×T×3). For the configuration used in this reference: N = 300, T = 400.

1.3 Flattening for the autoencoder

The fully-connected autoencoder requires a flat 1D vector as input. Each trajectory matrix is unrolled into a single row vector:

$$\tau_{\text{flat}} = \operatorname{flatten}(\tau) \in \mathbb{R}^{T \times 3} = \mathbb{R}^{400 \times 3} = \mathbb{R}^{1200}$$
$$X_{\text{flat}} \in \mathbb{R}^{300 \times 1200}$$

Reshape used directly by this codebase (main.py: clean.reshape(N_TRAJECTORIES, -1)); a standard flattening step for fully-connected autoencoders, not a distinct literature result on its own.

2. Spiral Trajectory Generation Function

2.1 Parametric definition

Professor comment — §2.1 justified
"In the writeup for the thesis, leave the number of steps in the trajectory as a variable."

All definitions below use T as a free variable. The reported experiments in this document use T = 400; this is a chosen experimental setting, not part of the general theory, and other values of T do not change any equation in this section.revised

$$t = \operatorname{linspace}(0, t_{\max}, T) \implies \Delta t = \frac{t_{\max}}{T-1}$$
$$r(t) = r_0 + kt$$radius at time t
$$x(t) = r(t)\cos(t) = (r_0 + kt)\cos(t)$$
$$y(t) = r(t)\sin(t) = (r_0 + kt)\sin(t)$$
$$z(t) = v_z \, t$$

Custom parametric spiral defined for this thesis (trajectory.py: generate_spiral_trajectory); an original construction, not adapted from a cited source.

The four parameters are independently randomized per trajectory:

  • $r_0 \sim \text{Uniform}(0.5, 1.5)$ — starting radius
  • $k \sim \text{Uniform}(-0.2, 0.2)$ — radius growth rate (positive = expanding, negative = contracting)
  • $v_z \sim \text{Uniform}(-0.5, 0.5)$ — vertical speed
  • $t_{\max} \sim \text{Uniform}(2\pi, 6\pi)$ — total arc (1 to 3 full rotations)
Note on r(t)
If k is sufficiently negative and t_max sufficiently large, r(t) can become negative within the sampled range, which flips the trajectory to the opposite side of the origin rather than producing a true contracting-then-reflecting spiral. This is a property of the current parameter ranges in trajectory.py, not a modeling error, but is worth stating explicitly if a strictly non-negative radius is assumed elsewhere in the thesis.

2.2 Intrinsic dimensionality of the generator

Each trajectory is fully determined by exactly 4 scalar parameters: $r_0, k, v_z, t_{\max}$. This means the generating process has 4 degrees of freedom, even though each trajectory is represented as a vector in $\mathbb{R}^{1200}$. This is a statement about how the data was generated — it does not by itself establish what dimensionality the trained autoencoder discovers or uses internally (see §8).revised

3. Noise Model

3.1 Gaussian noise addition

Given a clean trajectory $\tau_{\text{clean}}$, the noisy observation is $\tau_{\text{noisy}}(t) = \tau_{\text{clean}}(t) + \varepsilon(t)$, with $\varepsilon(t) = (\varepsilon_x, \varepsilon_y, \varepsilon_z)(t)$, each component drawn i.i.d. from $\mathcal{N}(0, \sigma^2)$.

Additive isotropic Gaussian noise is one of the corruption processes analyzed for denoising autoencoders in Vincent et al. [1][2].

Professor comment — §3.2 (i) justified
"Give some interpretation what this number means."

$\sigma = 0.6$ is the noise standard deviation, not its power. The expected noise power per coordinate is $\sigma^2 = 0.36$. Under the Gaussian model, about 68% of individual perturbations lie within $\pm 0.6$ of the clean value, and 95% within $\pm 1.2$. Whether $\sigma = 0.6$ counts as "moderate" noise depends on the scale of the trajectory itself (radius range $\approx 0.5$–$1.5$, so a single perturbation can be comparable in magnitude to the signal); this should be supported empirically with an input SNR figure, a clean/noisy overlay plot, and a comparison across multiple $\sigma$ values — all of which are produced by the current codebase (visualize.py: plot_snr_improvement, noise_sweep.py) rather than asserted from the formula alone.revised

3.2 Signal-to-noise ratio

Professor comment — §3.2 (ii) justified
"What exactly is P_signal and P_noise here? … τ_clean has also not been introduced. SNR is a useful metric to gauge efficiency of the AE but it needs some introduction."

Let $\tau_i^{\text{clean}}$ denote the clean trajectory for sample $i$, $\tau_i^{\text{noisy}} = \tau_i^{\text{clean}} + \varepsilon_i$ the noisy input, and $\hat{\tau}_i$ the autoencoder's reconstruction. In this context, "signal" always refers specifically to the clean trajectory $\tau_i^{\text{clean}}$ — the two terms are used interchangeably below, and $P_{\text{signal}}$ is literally the average squared magnitude of the clean trajectory, not a separate quantity. Define:revised

$$P_{\text{signal}} = \operatorname{mean}\!\left((\tau_i^{\text{clean}})^2\right)$$power of the clean trajectory itself
$$P_{\text{noise,before}} = \operatorname{mean}\!\left((\tau_i^{\text{noisy}} - \tau_i^{\text{clean}})^2\right)$$noise power before denoising
$$P_{\text{error,after}} = \operatorname{mean}\!\left((\hat{\tau}_i - \tau_i^{\text{clean}})^2\right)$$residual error power after denoising

The same decibel formula is then applied twice — once against the noise power before denoising, once against the residual error power after denoising — so the two numbers are directly comparable:revised

$$\text{SNR}_{\text{before}} \text{(dB)} = 10 \log_{10}\!\left(\frac{P_{\text{signal}}}{P_{\text{noise,before}}}\right)$$
$$\text{SNR}_{\text{after}} \text{(dB)} = 10 \log_{10}\!\left(\frac{P_{\text{signal}}}{P_{\text{error,after}}}\right)$$

The decibel form $10\log_{10}(P_{\text{signal}}/P_{\text{noise}})$ is the standard definition of signal-to-noise ratio for power quantities in signal processing (see the "Random Signals" appendix of a standard DSP text, e.g. Oppenheim & Schafer [10], where SNR for a signal corrupted by a random process is treated in general). A specific page/section number is not given here, since it has not been directly verified against a copy of the book. It is not autoencoder-specific; the denoising-specific part is only the choice of what to plug in for $P_{\text{signal}}$, $P_{\text{noise,before}}$, and $P_{\text{error,after}}$ (defined above), which follows this project's own implementation in visualize.py: plot_snr_improvement rather than a cited formula.

This matches the implementation in visualize.py: plot_snr_improvement, which computes $\text{SNR}_{\text{before}}$ and $\text{SNR}_{\text{after}}$ per trajectory, over a sampled subset of the test split.

4. Autoencoder Architecture

4.1 Overview

A denoising autoencoder (DAE) is trained to map a corrupted input back to its clean version [1]. It consists of an encoder that compresses the input into a low-dimensional latent representation, and a decoder that reconstructs the clean signal from that representation.

$$f : \mathbb{R}^{1200} \longrightarrow \mathbb{R}^{1200}$$input: noisy trajectory → output: reconstructed clean trajectory

Encoder/decoder decomposition f = Dec ∘ Enc follows the general denoising autoencoder formulation of Vincent et al. [1][2].

Professor comment — §4.3 (decoder / normalization) justified
"Try if it helps to normalize the trajectory before denoising."

Implemented in normalize.py and wired into main.py via the NORMALIZE flag: each trajectory is optionally scaled by its own per-trajectory factor $d_{\max,i} = \max_t \Vert x_{i,t} \Vert_2$ before the encoder sees it, and the decoder's output is multiplied back by the same stored d_max,i before computing MSE in original units. This lets the raw-coordinate and per-trajectory-normalized training regimes be compared directly on the same held-out test set, rather than asserted to help without measurement.revised

Professor comment — §4.5 (parameter count) justified
"That is already a quite heavy network, try what happens if you use a leaner AE."

The network width is now configurable rather than fixed at a single hidden layer of 128. model.py's TrajectoryAE accepts a hidden_dims sequence and builds a tapered stack of Linear → ReLU layers from input_dim down to embedding_size, mirrored in reverse for the decoder. The configuration used in this document is hidden_dims=(128, 64, 32) with embedding_size=16, i.e. a taper 1200 → 128 → 64 → 32 → 16, rather than a single 1200 → 128 → 8 jump. See §4.4 for the resulting shapes and parameter count.revised

4.2 Encoder (current configuration)

$$\text{Encoder} : \mathbb{R}^{1200} \to \mathbb{R}^{128} \to \mathbb{R}^{64} \to \mathbb{R}^{32} \to \mathbb{R}^{16}$$
$$h_1 = \operatorname{ReLU}(W_1 x_{\text{noisy}} + b_1), \quad W_1 \in \mathbb{R}^{128 \times 1200}$$
$$h_2 = \operatorname{ReLU}(W_2 h_1 + b_2), \quad W_2 \in \mathbb{R}^{64 \times 128}$$
$$h_3 = \operatorname{ReLU}(W_3 h_2 + b_3), \quad W_3 \in \mathbb{R}^{32 \times 64}$$
$$z = \operatorname{ReLU}(W_4 h_3 + b_4), \quad W_4 \in \mathbb{R}^{16 \times 32}, \quad z \in \mathbb{R}^{16}$$

Tapered fully-connected encoder, implemented in model.py: TrajectoryAE._build_mlp; the taper-toward-bottleneck pattern (vs. a single wide-to-narrow jump) reflects standard undercomplete-autoencoder design discussed in Goodfellow et al. [8], ch. 14.

Compression ratio: 1200 / 16 = 75×.

4.3 Decoder (current configuration)

$$\text{Decoder} : \mathbb{R}^{16} \to \mathbb{R}^{32} \to \mathbb{R}^{64} \to \mathbb{R}^{128} \to \mathbb{R}^{1200}$$
$$h_5 = \operatorname{ReLU}(W_5 z + b_5), \quad W_5 \in \mathbb{R}^{32 \times 16}$$
$$h_6 = \operatorname{ReLU}(W_6 h_5 + b_6), \quad W_6 \in \mathbb{R}^{64 \times 32}$$
$$h_7 = \operatorname{ReLU}(W_7 h_6 + b_7), \quad W_7 \in \mathbb{R}^{128 \times 64}$$
$$\hat{x} = W_8 h_7 + b_8, \quad W_8 \in \mathbb{R}^{1200 \times 128}$$no ReLU — coordinates can be negative

Mirrored decoder, implemented in model.py: TrajectoryAE._build_mlp (reversed hidden_dims); omitting the final activation for real-valued (possibly negative) targets is standard practice for regression-style autoencoder outputs, not attributed to a single specific source.

5. Activation Function — ReLU

$$\operatorname{ReLU}(x) = \max(0, x)$$

Rectified Linear Unit, as popularized for deep network hidden layers by Nair & Hinton [4].

Without a non-linear activation, stacking Linear layers collapses to a single linear map ($W_2 (W_1 x) = (W_2 W_1) x$), which cannot represent the non-linear spiral trajectory. ReLU breaks this linearity.

$$\mathcal{L}(W) = \frac{1}{N} \sum_{i=1}^{N} \Vert \hat{x}_i - x_i \Vert^2$$MSE between reconstruction and clean target

Standard mean-squared-error training objective; the Adam optimizer used to minimize it is due to Kingma & Ba [5].

6.3 Baseline MSE

Professor comment — §6.3 justified
"Explain what this is."

Two distinct baselines are relevant, and the original draft conflated them:revised

  • $\text{MSE}(0, \tau_{\text{clean}})$ — the zero-prediction baseline (predicting the all-zero vector), equal to the signal variance $\operatorname{Var}(\tau_{\text{clean}})$.
  • $\text{MSE}(\tau_{\text{noisy}}, \tau_{\text{clean}}) \approx \sigma^2$ per coordinate — the no-denoising baseline, i.e. the error you get by doing nothing at all. This is the relevant comparison for measuring what the autoencoder actually contributes, and is what main.py computes and prints as baseline_mse alongside the model's test MSE and the improvement ratio.

7. Training Procedure

Professor comment — §7.1–7.3 justified
"Show loss over training in a plot. You can also try if L-BFGS can further reduce the loss."

Training/validation loss by epoch is plotted and saved every run (visualize.py: plot_training_curve, saved as loss_curve.png). An L-BFGS full-batch optimizer is available as an alternative to Adam (train.py: _train_lbfgs, selected via optimizer_name="lbfgs"), intended as a short controlled comparison rather than a default — L-BFGS is a full-batch, second-order method with materially different convergence behavior than minibatch Adam, so results are compared on MSE, SNR, and wall-clock runtime rather than assumed to be better.revised

L-BFGS is a quasi-Newton optimization method; see Liu & Nocedal [9] for the algorithm as implemented in train.py: _train_lbfgs.

7.4 Train / validation / test split

Professor comment — §7.4 justified
"Typically you split into train / test / validation?"

The dataset is now split three ways rather than two: TRAIN_SPLIT = 0.6, VAL_SPLIT = 0.2, and the remaining 0.2 held out as a test set (main.py). The validation split drives early stopping and any hyperparameter/model selection; the test split is touched exactly once, after training is complete, to report the final MSE. This is an explicit fix for the earlier two-way train/test split, where the same held-out set was used both to pick the stopping point and to report the final number — a form of selection bias that the professor's comment specifically raised.revised

$$n_{\text{train}} = \lfloor N \times 0.6 \rfloor, \quad n_{\text{val}} = \lfloor N \times 0.2 \rfloor, \quad n_{\text{test}} = N - n_{\text{train}} - n_{\text{val}}$$

Three-way split matching this project's own main.py (TRAIN_SPLIT, VAL_SPLIT constants); a standard train/validation/test convention, not a single-source citation.

8. Why Compression Can Support Denoising

Professor comment — companion run-comparison document, §2–4 justified
"This would require a reference to a suitable theorem … [and] a proper definition of d*." / "Are you talking about subspaces or manifolds? These are not the same things." / "What are signal directions?" / "What does that mean?"
On the origin of the original text
Several claims in the original section — an explicit reconstruction-error formula in terms of an "intrinsic dimension" $d^*$, and the assertion $I(z;\, \text{noise}) \approx 0$ as if it were a proven property of this network — read like plausible-sounding generative text rather than results drawn from a specific theorem. That is a reasonable thing to happen when drafting with an LLM's help, and is consistent with guidance for AI-assisted academic writing at TUHH: AI tools may assist with structuring or phrasing, but claims presented as established results must be traceable to an actual source, and unverified or fabricated claims are not acceptable in submitted work. The revision below keeps the genuinely-supported ideas, cites where they come from, and explicitly flags what remains an informal, uncited intuition rather than a theorem.

A denoising autoencoder is not merely reproducing its input; because the training target is the clean trajectory while the input is noisy, the network is pushed to map corrupted points back toward the region where clean data actually lives. This "manifold" or "concentration of data" perspective — that training examples cluster near a lower-dimensional structure within the ambient input space, and a good representation is one robust to corruption of that input — is the perspective originally proposed by Vincent et al. [1][2], and is the correct citation for this idea rather than an unreferenced assertion.revised

Vincent et al. [2] also report a controlled comparison directly relevant to why noise-corruption training matters, separately from any capacity constraint: they trained an over-complete autoencoder (200 hidden units, more than the input dimension) two ways — once with L2 weight-decay regularization and no noise, and once as a denoising autoencoder with isotropic Gaussian noise ($\sigma = 0.5$) and no weight decay. The two conditions produced qualitatively different learned filters: weight decay alone yielded uninformative "blob" detectors, while denoising with sufficient noise produced sharp, oriented Gabor-like edge detectors resembling receptive fields in primary visual cortex. Their conclusion was that noise-based denoising training and weight-decay regularization are not interchangeable, even though both nominally prevent a trivial identity mapping.revised

This finding is cited here as motivating context for why the noise-corruption step in this project's training procedure (noise.py: add_gaussian_noise, applied before every forward pass in train.py) is doing something distinct from capacity control alone — not as a result reproduced on trajectory data. Two concrete differences from the original experiment should be stated plainly: (1) TrajectoryAE's architecture is under-complete (bottleneck of 16 units, narrower than the 1200-dimensional input; see §4.2), unlike the over-complete 200-unit layer Vincent et al. used to isolate the noise-only effect from any bottleneck effect — in this project's setup, compression and noise-robustness pressures act together, not in isolation; and (2) this codebase does not implement an L2-weight-decay training condition or a noise-off control run, so no equivalent "denoising vs. weight decay" comparison has actually been performed here. Running that comparison (e.g. adding weight_decay to the Adam optimizer in train.py and a NOISE_SIGMA=0 control) would be needed before claiming this project's results confirm the same qualitative distinction for 3D trajectories.revised

Separately, the encoder must pass information through a bottleneck layer much narrower than the input (16 units vs. 1200). Bounding the bottleneck's capacity is a classical way to prevent an autoencoder from learning the trivial identity map, and is discussed as a representation-learning constraint by Bengio et al. [3]. Some authors additionally analyze such bottlenecks through an information-theoretic lens — the "information bottleneck" framework of Tishby and Zaslavsky [6], which frames a layer's representation as trading off mutual information with the input against mutual information with the target.revised

What is not claimed here
The original draft's formula $\mathbb{E}\Vert \hat{x} - x \Vert^2 \approx \sigma^2 \cdot d^*/k + C(k)$ and the statement $I(z;\,\text{noise}) \approx 0,\ I(z;\,\text{signal}) \gg 0$ are not established results for this network. The information bottleneck framework, when applied to deep networks, is itself an active and disputed research question — Saxe et al. [7] directly challenge some of the empirical claims in Tishby and Zaslavsky's original account of how mutual information evolves during training. No mutual-information estimate has been computed for this model, and no citation supports the specific d*/k decomposition as written. This document therefore does not assert an intrinsic dimension for the trained latent space, and treats the noise-suppression explanation as a plausible, literature-consistent intuition rather than a proven property of TrajectoryAE.revised

What can be stated with the evidence actually available from this codebase: the clean spiral family is generated from 4 independent scalar parameters (§2.2) — a property of the generator, not a measured property of the trained model's latent space; and empirically, denoising performance (test MSE, SNR improvement) can be measured directly and compared across embedding sizes and noise levels via bottleneck_ablation.py and noise_sweep.py, which is the appropriate way to support any claim about how bottleneck width affects reconstruction quality for this specific dataset and architecture.revised
